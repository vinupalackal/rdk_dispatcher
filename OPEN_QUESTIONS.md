# RDK Dispatcher — Consolidated Open Questions

Every open item across this project's docs, gathered in one place so
nothing stays scattered. Grouped by status. When a change resolves an
item here, update its status rather than deleting the row — this file
is the project's running record of what's actually settled versus
still assumed.

| A7 | Is payload-level encryption required beyond transport TLS, and how do static (definition) vs. dynamic (command) WRP pushes route on the device? | `openspec/changes/require-payload-encryption-and-message-routing/` — yes, required eventually; **phased 2026-08-13: encryption is Phase 2 work.** Phase 1 uses plain JSON-RPC with the `static`/`dynamic` type field always present (message kind, a different axis from `load_type`), with verification still mandatory throughout. | A9 | Does Dispatch Core's claimed portability (NFR-1) hold up against RDK-B's CCSP/sysevent/Netlink coupling — does the plane model even apply to RDK-V the same way? | `openspec/changes/define-plane-vs-toolset-model/` (Decision D, added 2026-08-13) — **yes, identical implementation required.** The coupling is isolated behind a per-platform event namespace: toolset `events` entries resolve against a platform-supplied namespace table at load time, not compiled into Dispatch Core. RDK-B and RDK-V may share a namespace entry or diverge per event, at the platform integrator's discretion — Dispatch Core's own routing/ACL/lifecycle code never branches on platform | **Confirmed** — namespace table authoring mechanism itself still open, see that change's `tasks.md` §5 |
| A10 | RDM Client's install/rollback unit is a whole toolset package (FR-11/FR-12) — how does this reconcile with a toolset containing per-plugin static/dynamic sub-parts? | `openspec/changes/define-synchronous-toolset-push/` (added 2026-08-13) — **unit stays whole-package, unchanged.** A toolset needing new device-level (compiled/`dlopen()`-able) code gets that code built and delivered as part of its one package via RDM, same as any toolset install — never as a separate per-sub-plugin artifact. RDM's install cycle stays asynchronous for now; making it feel more synchronous over time is a stated aspiration, not a scheduled design | **Confirmed** |
| A11 | Should config/state-reads be modeled as MCP resources, distinct from invocable MCP tools, or should everything stay unified as tools? | `openspec/changes/define-toolset-as-mcp-tool-model/` (added 2026-08-13) — **phased: triage plane keeps its current unified-tools model, unchanged; the resources-vs-tools question for config/management/control planes is deferred to Phase 2**, when those toolsets get a concrete design rather than being assumed | **Confirmed, phased** — Phase 1 unchanged; other planes decided in Phase 2 |
| A12 | Does `tools/call` become the only supported command shape, or does a non-MCP JSON-RPC 2.0 path stay supported indefinitely? | `openspec/changes/define-toolset-as-mcp-tool-model/` (added 2026-08-13) — **confirmed: two permanently coexisting shapes.** Low duplication risk because both converge on one execution path (ACL, resolution, sandboxing written once); the real, permanent cost is two framings/parsers, doubled docs/test coverage, and needing to keep re-verifying both shapes hit the same ACL checkpoint on every future change (now explicit scope for B4's security review) — full advantages/bottlenecks list in that change's `design.md` | **Confirmed** |
| A13 | Is "each plugin's MCP tool identity" scoped per-method (`wifi.setChannel`), or should some plugins be exposed as coarser, single MCP tools with the method as a structured argument? | `openspec/changes/define-toolset-as-mcp-tool-model/` (revised 2026-08-13) — **confirmed: coarser, one MCP tool per toolset.** `tools/list` entry `name` = the toolset (not `<toolset>.<method>`); `inputSchema` becomes a `oneOf` discriminated union, one branch per method, each requiring a `method` const plus that method's own `params` schema. ACL Policy Store's per-method granularity is explicitly unaffected — the query API already took toolset and method as separate values, so the catalog getting coarser doesn't coarsen what a grant actually covers. Trade-off named, not hidden: smaller catalog, but an MCP client now needs to inspect the `oneOf` schema to discover per-method detail instead of reading it off a flat tool name | **Confirmed** — schema legibility at real method-count scale still to be watched, see that change's `tasks.md` §2a |
| A14 | `notifications/tools/list_changed` and `capability-sync`'s device-identity-authenticated push fire from the same trigger and read the same data through two separate mechanisms — should this stay permanently separate, or should one become the other's source? | `openspec/changes/define-toolset-as-mcp-tool-model/` (revised 2026-08-13) — **confirmed: stay permanently separate deliveries; neither becomes the other's source** (mismatched reliability profiles — a retry/backoff cycle on the durable catalog push must never delay or block the live session notification). **What changed:** both now SHALL be fanned out from one shared emission point in Plugin Manager, closing the risk of silent drift from two independently-written listeners, without introducing any coupling between their two independent downstream queues | **Confirmed** — implementation tasks in that change's `tasks.md` §1a |
| A15 | Should real command execution and `toolset.push` move into Phase 1, ahead of the rest of Phase 2's out-of-process/sandboxing work? | `openspec/changes/add-phase1-command-execution-exception/` (added 2026-08-14) — **confirmed, narrowly scoped, per three direct answers:** (1) only command execution + `toolset.push` move up — RBUS/Thunder mapping, sandbox authoring workflow, footprint sizing, RDK-V namespace mapping, and the concluding security review stay Phase 2; (2) sandboxing is an **explicit, reviewed exception** — Phase 1's command-executing toolset(s) run in-process, invoking the escape-valve clause `define-plane-vs-toolset-model` reserved for exactly this, ACL enforcement (FR-4) unaffected; (3) encryption stays Phase 2, unchanged (A7). `toolset.push`'s RDM boundary (A6) and verification are unchanged; its Phase 1 rollback is a health-check-gated in-process swap, not the artifact-fallback model designed for Phase 2's on-demand execution | **Confirmed** — A1, C8, and `docs/20`'s ACL design (B5/B6) are now Phase 1 blockers as a direct consequence, not Phase 2-paced anymore |
